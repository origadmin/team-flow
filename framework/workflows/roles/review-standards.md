**⚠️ 创建任何文档时，必须先检查路径！**

**内部文档 → `{docs_internal}`**

```
   - 存放位置: [{docs_internal}/{docs_external}]
   - 路径: xxx/xxx.md
```

## 2. 审查维度

### 2.1 必查项

| 维度 | 检查点 | 阻塞级别 |
|------|--------|---------|
| **功能正确性** | 业务逻辑实现正确 | P0 |
| **功能正确性** | 边界条件处理 | P0 |
| **功能正确性** | 异常处理完整 | P0 |
| **代码质量** | 无明显性能问题 | P1 |
| **代码质量** | 无安全漏洞 | P0 |
| **代码质量** | 命名规范清晰 | P2 |
| **代码质量** | 无重复代码 | P2 |
| **测试覆盖** | 单元测试覆盖 | P1 |
| **测试覆盖** | 测试用例合理 | P1 |
| **文档** | API 文档更新 | P2 |
| **文档** | 关键逻辑有注释 | P3 |

### 2.2 按语言专项检查

**Go**
- 错误处理（不使用 `panic`，错误需返回）
- 并发安全（goroutine 泄漏、数据竞争）
- 依赖管理（go.mod 干净）

**前端 (React/TypeScript)**
- 类型安全（无 `any` 滥用）
- 组件复用（无重复代码）
- 状态管理（无状态泄漏）

## 4. 审查流程

### 4.1 Author 职责

1. 确保 CI 全部通过后再提 Review
2. PR 描述必须包含：做了什么、为什么改、怎么测试
3. 响应所有审查意见
4. 修改完成后重新请求审查

### 4.2 Reviewer 职责

1. 24 小时内完成审查
2. 提供具体、可操作的修改建议
3. 区分阻塞性问题和优化建议
4. 审查通过后自行合并（不允许 Author 代合并）

---

## 5. 审查 Checklist

### 5.1 功能正确性

- [ ] 代码逻辑与设计文档一致
- [ ] 边界条件已覆盖（空值、最大值、非法值）
- [ ] 异常情况有处理
- [ ] 并发场景安全

### 5.2 代码质量

- [ ] 命名规范、清晰
- [ ] 无重复代码（DRY 原则）
- [ ] 无硬编码配置
- [ ] 错误处理规范
- [ ] 无安全漏洞（SQL 注入、XSS 等）

### 5.3 测试覆盖

- [ ] 单元测试覆盖核心逻辑
- [ ] 测试用例有实际验证意义
- [ ] 测试数据合理

### 5.4 文档

- [ ] API 变更有文档
- [ ] 关键逻辑有注释
- [ ] README 已更新（如需要）
