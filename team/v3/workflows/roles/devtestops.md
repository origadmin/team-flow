# DevTestOps 全流程质量保障 — team-flow v2 (beads-native)

> **适用**: 所有开发任务的质量门禁
> **前置**: 先读 `{TEAM_PATH}/workflows/shared.md` 了解通用原则
> **参考**: test-levels.md（变更类型→测试级别）、specialized-tests.md（专项测试触发规则）、checklist.md（提测准入基线）

---

## 1. 适用场景

- 开始新需求/功能开发，需要确定测试策略
- 代码开发完成，准备提测前的自检
- 需要判断当前变更需要哪些级别的测试
- 需要确认是否满足提测准入基线
- 上线前的最终检查
- 上线后的观察验收

不适用：纯文档修改、注释调整等不涉及逻辑变更的场景。

---

## 2. 核心原则

1. **核心链路必须验证** — 主流程跑不通不能提测
2. **高风险专项必须补充** — 触发条件命中时必须做
3. **提测准入有底线** — 基础项没过不进正式提测
4. **上线不只看启动** — 要看接口、链路、日志、指标、告警

---

## 3. 执行流程

### Step 0：判断当前阶段

收到任务后，先判断当前处于哪个阶段：

| 用户意图 | 对应阶段 | 执行路径 |
|---------|---------|---------|
| "分析需求""需求评审" | 阶段 1 需求澄清 | 执行 Step 1 |
| "设计方案""技术评审" | 阶段 2 方案与用例准备 | 执行 Step 2 |
| "写完了""自测""跑测试" | 阶段 3 基础质量验证 | 执行 Step 3 |
| "联调""集成测试""E2E" | 阶段 4 主链路验证 | 执行 Step 4 |
| "专项测试""性能测试" | 阶段 5 专项与性能 | 执行 Step 5 |
| "提测""准备提测""能提测吗" | 阶段 6 提测与回归 | 执行 Step 6 |
| "上线""发布""上线观察" | 阶段 7 上线与观察 | 执行 Step 7 |
| 不确定 | — | 先读代码和 git diff 判断变更范围，再推荐阶段 |

### Step 1：需求澄清

**开发侧**：
- [ ] 需求范围明确，边界条件已定义
- [ ] 验收标准可量化、可测试
- [ ] 风险点已识别并记录
- [ ] 依赖项（外部接口、第三方服务）已确认

**测试侧**：
- [ ] 需求已分析，测试范围已圈定
- [ ] 高风险场景已标记
- [ ] 测试数据需求已明确

**输出**：需求澄清确认，可进入方案设计。

### Step 2：方案与用例准备

**开发侧**：
- [ ] 接口设计已完成（入参、出参、错误码）
- [ ] 状态流转已定义
- [ ] 异常处理方案已明确
- [ ] 并发和回滚方案已考虑

**测试侧**：
- [ ] 测试计划已编写
- [ ] 测试用例已覆盖：主流程、异常流程、边界场景
- [ ] 用例已按优先级排序（P0 > P1 > P2）

**输出**：方案和用例就绪，可进入编码。

### Step 3：基础质量验证

**判定变更类型**：读取 test-levels.md，根据 git diff 判定变更类型。

```
变更类型判定：
├─ 纯逻辑调整    → 单元 + 模块 + 回归
├─ 接口改动      → + API 测试 + 兼容性
├─ 跨模块改动    → + 集成测试 + 数据一致性
├─ 核心链路改动  → + E2E + 专项测试
└─ 高风险改动    → + 性能基准 + 回滚演练 + 灰度方案
```

**执行**：
- [ ] 单元测试全部通过（覆盖率 ≥ 80%）
- [ ] 模块测试通过（组件与直接依赖联动正常）
- [ ] 无 lint/typecheck 错误
- [ ] 代码无调试残留（console.log、TODO hack、注释掉的代码）

**输出**：基础质量通过，可进入主链路验证。

### Step 4：主链路验证

- [ ] 核心业务流程从头到尾跑通
- [ ] 前后端/服务间调用正常
- [ ] 状态流转完整（从起始到终态）
- [ ] 数据落库/页面展示/消息发出正确

**输出**：主链路通过，可进入专项测试。

### Step 5：专项与性能

读取 specialized-tests.md，逐条匹配触发条件。命中则标记为"必须测"，未命中标记为"跳过"并附理由。

**后端 8 类专项测试**（读取 specialized-tests.md）：
1. E2E 测试 — 核心主链路、跨模块流程
2. 接口/API 测试 — 接口变更、鉴权、兼容性
3. 权限与安全 — 登录态、角色、敏感字段
4. 并发/幂等/重试 — 扣减、提交、状态流转
5. 数据一致性 — DB、缓存、队列、账务
6. 异步任务/队列 — 消息队列、定时任务、死信
7. 配置与兼容性 — 开关、灰度、老数据
8. 回滚与可观测性 — 发布、迁移、监控

**前端 10 类专项测试**（读取 frontend-specialized-tests.md）：
1. 组件渲染测试 — 渲染正确性、条件分支、加载/空/错误状态
2. 用户交互测试 — 点击、输入、表单提交、快捷键
3. Hook 逻辑测试 — 状态转换、副作用、边界值
4. API 集成测试 (MSW) — Mock API → 组件流程、CRUD
5. 路由守卫测试 — 认证重定向、权限检查、参数传递
6. 响应式布局测试 — 断点切换、侧边栏折叠、网格调整
7. 可访问性测试 — ARIA 角色、键盘导航、焦点管理
8. 状态管理测试 — AuthContext、TanStack Query 缓存
9. 国际化测试 — 语言切换、缺失翻译、格式化
10. 主题测试 — CSS 变量、主题切换、持久化

**判断规则**：
- 后端变更 → 匹配后端 8 类
- 前端变更 → 匹配前端 10 类
- 全栈变更 → 两边都匹配

未命中任何触发条件时，跳过本阶段。

**输出**：专项测试结果。命中项已验证 / 未命中项已说明跳过原因。

### Step 6：提测与回归

**Step 6.1 提测准入检查**

读取 test-levels.md，按变更类型逐项检查准入基线。

每项检查结果标注红绿灯：
- 🟢 已通过（附证据：测试命令输出 / 测试报告链接）
- 🟡 部分通过（附说明：哪些子项未覆盖 + 风险评估）
- 🔴 未通过（附阻塞原因 + 修复建议）
- ⚪ 不适用（附跳过理由）

**准入判定**：
- 全部 🟢 → 建议提测
- 有 🟡 无 🔴 → 风险提测，需记录未覆盖项
- 有 🔴 → 不建议提测，需修复后重新检查

**Step 6.2 提测资料检查**

- [ ] 变更说明完整（改了什么、为什么改、影响范围）
- [ ] 已知问题已记录（带 workaround 或修复计划）
- [ ] 测试环境可用
- [ ] 测试数据已准备

**Step 6.3 回归测试**

- [ ] 缺陷修复后重测通过
- [ ] 相关链路回归通过（不只测缺陷点）
- [ ] 无新增回归问题

**输出**：提测准入报告（红绿灯标识）。

### Step 7：上线与观察

**上线验证清单**：
- [ ] 核心接口响应正常（状态码、延迟、错误率）
- [ ] 关键业务链路可跑通
- [ ] 日志无异常报错（grep error/panic/fatal）
- [ ] 指标和告警正常（CPU、内存、goroutine、队列堆积）
- [ ] 异常回流渠道畅通（告警能触发、oncall 能收到）
- [ ] 回滚方案可执行（步骤明确、已演练）

**输出**：上线观察报告。

## 5. 质量门禁（等效 Hook 逻辑）

以下规则等效于 Claude Code 的 Hook 机制，任何 Agent 必须遵守：

### 5.1 编辑后验证（等效 PostToolUse Hook）

编辑任何源码文件后，必须执行对应语言的检查：

| 文件类型 | 必须执行 |
|---------|---------|
| `.go` | `gofmt -l` + `go vet ./...` |
| `.ts` `.tsx` | `tsc --noEmit`（或项目配置的类型检查） |
| `.js` `.jsx` | `eslint`（如项目配置） |
| `.py` | `ruff check` 或 `flake8` |
| `.rs` | `cargo check` |
| `.vue` | `vue-tsc --noEmit`（本项目禁止使用 Vue） |

**规则**：lint/typecheck 不通过 → 不允许继续下一步。必须先修复。

### 5.2 收尾前验证（等效 Stop Hook）

任务结束前，如果存在未提交变更，必须：

1. 跑项目测试命令（根据环境检测：`bun test` / `npm test` / `make test` / `go test ./...`）
2. 测试通过才允许结束
3. 测试不通过 → 不允许声明"完成"，必须修复

### 5.3 敏感文件拦截（等效 PreToolUse Hook）

禁止将以下文件类型提交到 git：
- `.env` `.env.*` `.pem` `.key` `.secret` `.pfx` `.p12`
- `credentials.json` `id_rsa`

**发现暂存区包含敏感文件时**：
1. 取消暂存：`git restore --staged <file>`
2. 加入 `.gitignore`
3. 确认无误后重试 commit
