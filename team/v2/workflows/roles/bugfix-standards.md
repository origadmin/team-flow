| 项目配置 | 追踪方式 |
|---------|---------|

## 3. Bug 报告生命周期

> **核心原则**: 用户只需说"有问题"，其余由 AI 负责。

```
发现 → 补充 → 分析 → 修复 → 关闭
```

### 3.1 发现阶段

**用户**: "第三步卡住了"
**AI**: 生成草稿 → 标注缺失项 → 提问用户

```markdown
# BUG-001

**Bug ID**: BUG-001
**发现时间**: {YYYY-MM-DD HH:mm}
**发现人**: 用户
**当前状态**: 待补充

---

## 用户描述（原始）
[直接引用用户原话]

---

## AI 自动补充

**Bug 表现**: [待确认]
**复现步骤**: [待确认]
**预期行为**: [待确认]
**实际行为**: [待确认]

---

## 待确认项

| 序号 | 字段 | 缺失原因 | 优先级 |
|------|------|---------|--------|
| 1 | 复现步骤 | "第三步"指哪一步？ | P0 |
| 2 | 预期行为 | 应该怎样？ | P0 |
| 3 | 实际行为 | 现在怎样？ | P0 |
| 4 | 环境信息 | 什么浏览器/系统？ | P1 |
| 5 | 截图/日志 | 有错误信息吗？ | P1 |

---

## AI 提问

1. **"第三步"是指什么操作？**（上传/切片/查询/其他）
2. **卡住的表现是什么？**（一直转圈/超时/报错）
3. **有截图或错误信息吗？**
4. **使用的浏览器和操作系统？**
5. **能复现吗？**（每次都这样/偶尔/只这一次）
```

### 3.2 补充阶段

**用户**: 回答问题 / 提供截图 / 补充描述
**AI**: 更新文档 → 继续补充 → 文档完善

```markdown
# BUG-001（已补充）

**Bug ID**: BUG-001
**当前状态**: 分析中

---

## 用户补充信息

| 序号 | 补充内容 | 来源 |
|------|---------|------|
| 1 | "第三步" = 切片那步 | 用户回答 |
| 2 | 卡住 = 一直转圈，没有进度更新 | 用户回答 |
| 3 | 用的 Chrome / Windows 11 | 用户补充 |

---

## AI 更新后的完整描述

### Bug 表现
切片步骤进行时，界面一直显示转圈，没有进度更新。

### 复现步骤
1. 登录系统
2. 进入上传页面
3. 选择视频文件（约 500MB）
4. 点击上传
5. 上传成功后自动进入切片步骤 ← **卡在这里**
6. 切片进度一直为 0%

### 预期 vs 实际
- **预期**: 切片进度从 0% 逐步增加到 100%
- **实际**: 切片进度始终为 0%，一直等待

### 环境信息
- 浏览器: Chrome
- 操作系统: Windows 11
- 视频大小: 约 500MB

---

## 待排查项（AI 标注）

| 序号 | 待排查项 | 负责方 | 状态 |
|------|---------|-------|------|
| 1 | 后端切片服务是否正常响应 | 后端 | 🔄 |
| 2 | 切片状态轮询接口是否工作 | 前端 | ⏳ |
| 3 | 切片超时设置是否合理 | 后端 | ⏳ |
```

### 3.3 分析阶段

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 根因分析 | AI 补充根因分析 |
| 2 | 责任分配 | AI 标注责任方（前端/后端/共同） |
| 3 | 修复方案 | AI 提出修复方案 |
| 4 | 影响评估 | 评估影响范围和相关问题 |

### 3.4 修复阶段

| 步骤 | 操作 |
|------|------|
| 1 | 实施修复 |
| 2 | 验证测试 |
| 3 | 回归测试 |
| 4 | 更新 Bug 报告状态 |

### 3.5 关闭阶段

> **强制步骤**: 检查其他 open 的 Bug 是否受影响

```markdown
## 关闭检查

### 相关问题检查（强制）

| 关联 Bug | 关联原因 | 状态 | 处理 |
|---------|---------|------|------|
| BUG-002 | 可能与切片逻辑相关 | open | 确认不受影响 |
| BUG-003 | 无关 | open | 无需处理 |

### 关闭确认

- [x] 修复已验证
- [x] 回归测试通过
- [x] 相关问题已检查
- [x] 文档已完善

**当前状态**: closed
**关闭时间**: {YYYY-MM-DD HH:mm}
```

### AI 行为规则

| 规则 | 说明 |
|------|------|
| **不能瞎填** | 不知道的字段标注 `[待确认]`，不得自行假设 |
| **必须提问** | 缺少 P0 信息时，必须向用户提问，不得跳过 |
| **文档是活的** | 报告可以多轮迭代，不是一次性完成 |
| **闭环检查** | 修复完成后必须检查其他 open 的 Bug 是否受影响 |

### 状态流转

```
open → needs_info → analyzing → in_progress → verified → closed
```

## 4. Bug 分类体系

### 4.1 按问题根因分类

| 根因类型 | 描述 | 示例 | 修复复杂度 |
|---------|------|------|----------|
| **代码 Bug** | 代码本身逻辑错误 | 空指针、边界条件未处理 | 低~中 |
| **设计缺失** | 代码正常，设计不完整 | 缺少字段设计、缺少状态定义 | 中 |
| **流程缺失** | 根本性流程未设计 | 缺少业务流程、缺少审核流程 | 高 |
| **环境问题** | 代码正常，环境配置错误 | DB 连接串错误、缓存未开启 | 低 |
| **集成问题** | 单模块正常，集成后失败 | 接口不匹配、协议不一致 | 中 |
| **数据问题** | 代码正常，数据本身异常 | 数据脏读、索引损坏 | 低 |
| **第三方依赖** | 外部服务/库变更导致 | API 升级、SDK 版本不兼容 | 中 |
| **性能问题** | 功能正常，性能不达标 | 查询慢、内存泄漏 | 中 |
| **安全问题** | 功能正常，存在安全隐患 | SQL 注入、XSS 漏洞 | 中 |
| **边界条件** | 正常情况正常，边界情况失败 | 空数组、超长字符串 | 低 |
| **并发问题** | 单用户正常，多用户异常 | 库存超卖、重复提交 | 高 |

### 4.2 按修复范围分类

| 修复范围 | 对应根因 |
|---------|---------|
| **局部修复** | 代码 Bug、环境问题、数据问题、边界条件 |
| **跨模块修复** | 设计缺失、集成问题、并发问题 |
| **体系重构** | 流程缺失、性能问题、安全问题 |

### 4.3 分类决策树

```
Bug 分析
  │
  ├─ 代码本身有 Bug？
  │    ├─ 是 → 代码 Bug（局部修复）
  │    └─ 否 → 下一步
  │
  ├─ 设计是否完整？
  │    ├─ 否 → 设计缺失 Bug（跨模块修复）
  │    └─ 是 → 下一步
  │
  ├─ 流程是否存在？
  │    ├─ 否 → 流程缺失 Bug（体系重构）
  │    └─ 是 → 下一步
  │
  └─ 其他问题？（环境/数据/第三方/性能/安全/边界/并发）
```

## 5. 责任分配体系

### 5.1 判定原则

| 判定原则 | 说明 |
|---------|------|
| **谁产生数据** | 谁负责数据准确性 → 后端 |
| **谁处理逻辑** | 谁负责逻辑正确性 → 后端 |
| **谁展示数据** | 谁负责展示正确性 → 前端 |
| **接口层** | 后端负责接口契约，前端负责正确调用 |

### 5.2 责任分配迭代

> 责任分配也可能错误（初步判断是前端，实际是后端），需要记录迭代过程。

| 迭代 | 时间 | 判断 | 责任方 | 依据 | 结果 |
|------|------|------|-------|------|------|
| 迭代 1 | 04-15 10:00 | 前端 | 前端 | 页面显示异常 | ❌ 排除 |
| 迭代 2 | 04-15 14:00 | 后端 | 后端 | 接口数据问题 | ✅ 确认 |

### 5.3 协作场景处理

| 场景 | 处理方式 |
|------|---------|
| **单方可修复** | 责任方负责 |
| **双方都可修复** | 评估成本和风险，选择最优方案 |
| **接口问题** | 双方都要改，协调接口契约 |
| **初始判断错误** | 重新分配，记录迭代过程 |

## 八、⛔ R 递增强制触发规则

> **强制要求**：Bug 修复验证未通过时，执行角色**必须**创建 R{N+1} 目录并重置阶段，**禁止在当前 R 目录内覆盖修改**。

### 触发条件

| 触发条件 | 判断者 | 必须动作 |
|---------|-------|--------|
| Phase 3 验证结果为"未通过" | 执行角色（Bugfix/Dev） | 1. 创建 `{bug-id}-R{N+1}/` 目录 2. 通过 `flow tools beads update` 重置阶段为 Phase 1 3. 更新 beads issue 的 doc_path 为 R{N+1} 目录 |
| 用户反馈"还没修好" | 执行角色 | 同上 |
| AI 自测发现修复方向错误 | 执行角色 | 同上 |

### R 递增操作清单

```
验证未通过
    │
    ├── Step 1: 在当前 R 目录完成 SUMMARY.md（记录本轮失败原因）
    ├── Step 2: 创建新目录 {bug-id}-R{N+1}/
    ├── Step 3: flow tools beads update <task-id> --add-label phase:analyze（重置为 Phase 1）
    ├── Step 4: flow tools beads update <task-id> --set-metadata doc_path="...R{N+1}/"
    ├── Step 5: 在新 R 目录中进行新的 RCA 分析（不可跳过）
    └── Step 6: 继续修复流程
```

### 禁止

- ❌ 验证未通过时继续在当前 R 目录内修改（必须开新 R）
- ❌ 跳过 RCA 直接在新 R 目录中重试（每轮 R 必须重新分析失败原因）
- ❌ 未更新 beads issue 的 doc_path 就创建新 R 目录
- ❌ 删除或覆盖历史 R 目录

## 九、自测要求（强制）

> **强制要求**: 每次代码修改后必须执行自测，未通过自测不得提交或汇报完成。

### 9.1 自测流程

> ⚠️ **必须先执行命令检测（见 SKILL.md 步骤 5），不得直接使用下方命令！**

| 步骤 | 检查项 | 命令（示例：检测到 Go 后端） |
| 1 | 编译检查 | `go build ./...` |
| 2 | 单元测试 | `go test ./...` |
| 3 | 格式化验证 | `go fmt ./...` |
| 4 | Bug 修复验证 | 执行验收方案中的测试用例 |

### 9.2 自测未通过处理

| 检查项 | 未通过 | 处理方式 |
|--------|-------|----------|
| 编译 | 编译错误 | 修复后重新自测 |

| 格式化 | 格式问题 | 执行格式化后重新自测 |
| Bug 修复验证 | Bug 仍存在 | 重新分析并修复 |
