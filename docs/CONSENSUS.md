## 1. 项目定位

### 1.1 本项目是什么

team-flow 是一个**基于 Go 的 CLI 工具**，用于驱动 AI 团队协作流程。

- 它定义流程（flow）→ 驱动节点推进 → 管理任务生命周期
- 它不是一个 AI 模型，也不是一个通用的 AI 框架
- 它的核心价值是**通过结构化的流程驱动 AI 行为

### 1.2 v2 和 v3 的关系

- v2 和 v3 **完全分离**，互不依赖
- v2 的团队/流程定义不是 v3 的输入
- v3 的目标是替代 v2

### 1.3 当前状态

- active_flow = skill-dev-flow（当前项目级配置）

## 2. 架构共识

### 2.1 分层架构（不可违反

```
cmd/（命令注册） → internal/proc（引擎） → internal/task（服务） → internal/flow（数据模型）
```

- flow 包是纯数据层，**不依赖任何其他内部包**
- proc 包是核心执行层，依赖 flow、config、eventlog、session
- main 是薄的组装层，只负责注册命令和启动引擎

### 2.2 纯函数优先

核心业务逻辑必须写成纯函数（输入→输出，无副作用），副作用隔离在边缘。

验证：`internal/bd/client.go` 中的 `parseBeadsID()` 是纯函数，`RunQuiet()` 有副作用。

### 2.3 外部 CLI 集成的标准模式

- 薄封装层（`Run` / `RunQuiet`）→ 纯解析函数（`parseBeadsID`）→ 高层函数（`CreateIssue`）

## 3. 任务 ID 规范

### 3.1 ID 格式

✅ **正确格式**: `project-xxx` （由 beads CLI 生成）

- 必须包含连字符 `-`
- 第一部分是项目标识（如 `team-flow`）
- 第二部分是 beads 生成的唯一后缀

❌ **禁止格式**:
- 纯随机短码（如 `a26c80` 是节点 ID，不是任务 ID）
- `idgen.RandHex(n)` 生成的短 ID 只能用于 flow 节点 ID，不能用于任务 ID

### 3.2 为什么必须用 beads

- 一致的命名空间：每个项目的任务 ID 不会冲突
- 可追踪：beads 维护完整的任务生命周期
- 标准：所有使用 beads 统一任务管理系统

### 3.3 `flow task create` 的责任

```
flow task create --title "..."
         ↓
bd.CreateIssue() → bd CLI（生成 team-flow-xxx
         ↓
写入 .team/tasks/team-flow-xxx.json
```

### 3.4 这是共识，不可协商。

## 4. Flow 节点 ID 规范

### 4.1 节点 ID 是随机短码（如 `a26c80`

- 不是语义化名称，不编码含义
- 含义在 `name` 字段中
- 便于重构和替换节点实现

### 4.2 为什么不用语义化 ID

- 节点的"做什么"和"节点 ID"是两回事
- flow 的结构会变 — 节点含义不变
- 用随机 ID → 节点含义和实现可以独立演化

## 6. 测试共识

### 6.1 测试层级

| 层级 | 范围 | 工具 | 覆盖率要求 |
|------|------|------|----------|
| 单元测试 | 纯函数 | `go test` | 每个纯函数必须有 |
| 集成测试 | 模块间交互 | `go test` + 手动验证 | 核心流程必须有 |
| 端到端测试 | 完整 flow 路径 | 构建 flow 二进制 + 实际命令 | 每个主要命令必须有 |

### 6.2 单元测试优先级

1. 纯逻辑（parse 测试（核心逻辑必须是纯函数 → 100% 必须有单元测试
2. `internal/bd/client.go 中 parseBeadsID → 必须有
3. 新添加的纯函数 → 必须有

### 6.3 修改必须通过现有测试不通过 → 不改代码

## 7. Bug Fix 流程共识

### 7.1 流程

```
1. 复现问题 → 理解根本原因 → 写测试（证明问题存在）→ 修改代码 → 通过测试
→ 验证修复 → 验证没有回归 → 更新文档（如需要）

注意：第 4 步（写测试）在第 5 步（改代码）之前。
```

### 7.2 根本原因分析（Root Cause）

问题必须在 **理解**。不是表面修复，**不是**症状缓解。

**坏**: "flow task create 生成 4 位短 ID"

- 表面：task.go 中使用 idgen.RandHex(2)
- 根本原因：taskCreateV3() 没有调用 bd.CreateIssue()
- 修复：将 task.go 调用 bd.CreateIssue()

## 8. 流程引擎

### 8.1 `flow proc run` 的责任

- 必须在 project 目录下运行
- 必须有 .team/project.md 定义 active_flow
- 必须通过 `--analysis 和 `flow proc run --new` 启动新会话
- 必须通过 `flow proc run <node-id>` 推进到指定节点
- 必须通过 `flow proc next` 自动推进

### 8.2 节点推进语义

- `start` 节点 → 启动流程开始（初始化）
- `phase` 节点 → 实际工作（AI 在此阶段
- `gate` 节点 → 条件检查（tests_pass, deliverables_complete 等）
- `branch` 节点 → 条件分支
- `terminal` 节点 → 流程结束

## 10. 反模式黑名单

这些是明确禁止的做法：

| 模式 | 为什么坏 | 替代方案 |
|------|---------|---------|
| 混合副作用和纯逻辑在一个函数 | 不可测试，职责混乱 | 分离成副作用在纯函数 |
| 使用 CombinedOutput() 捕获 stdout+stderr | 警告信息干扰解析 | 使用 Output() 只捕获 stdout |
| 直接在命令行参数解析和业务逻辑写在一起 | 难测试，难维护 | 分离：解析层 + 业务层 |
| 没有文档就改代码 | 不知道为什么这样设计 | 先更新设计文档 |
| 没有测试就改代码 | 没有回归保证 | 先写失败测试，再改代码 |
| ID 用 idgen.RandHex(n) 作为任务 ID | 不遵循 beads 规范 | 调用 bd.CreateIssue() |
| 用语义化节点 ID（如 "session-start"） | 不可靠 | 随机短码 |
