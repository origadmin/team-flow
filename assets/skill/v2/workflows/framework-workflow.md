> 适用于框架开发团队（toolkits/runtime/contrib 模块）

```

  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐

       │              │              │              │              │
       ↓              ↓              ↓              ↓              ↓

## 框架模块架构

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           框架三层架构                                   │
└─────────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────┐
  │                            contrib                                   │
  │                    (外部系统实现，即插即用)                           │
  │  broker (watermill) | config | registry (consul/etcd) | security   │
  └─────────────────────────────────────────────────────────────────────┘
                                    ↑
                                    │ 依赖接口定义
  ┌─────────────────────────────────────────────────────────────────────┐
  │                            runtime                                   │
  │                   (go-kratos 封装，契约优先)                          │
  │  engine | config | contracts | registry | log | middleware | service │
  └─────────────────────────────────────────────────────────────────────┘
                                    ↑
                                    │ 依赖工具
  ┌─────────────────────────────────────────────────────────────────────┐
  │                            toolkits                                  │
  │                    (零框架依赖，基础工具链)                            │
  │  cache | codec | crypto | encoding | errors | metrics | uuidstr ...  │
  └─────────────────────────────────────────────────────────────────────┘

  ⚠️ 依赖单向性: toolkits → runtime → contrib，禁止反向和横向依赖
```

## Phase 1: 审计阶段（Framework Architect 主导）

**触发条件**: 新模块开发或定期代码审查

### 流程

```
1. Framework Architect 扫描模块目录结构
2. 分析代码实现状态（已完成/待开发/需重构）
3. 评估代码质量
4. 识别技术债务和风险
5. 输出审计报告和改进建议
```

### 产出物

| 文档 | 负责人 | 存放位置 |
|------|--------|---------|
| 审计报告 | Arch | `{docs_internal}/audit/{module}_AUDIT.md` |
| 改进计划 | Arch | `{docs_internal}/audit/{module}_ROADMAP.md` |

### 审计维度

- **实现状态**: 已完成 / 待开发 / 需重构
- **代码质量**: 可读性、可维护性、性能
- **测试覆盖**: 单元测试、集成测试
- **文档完整**: README、API 文档、示例
- **依赖关系**: 外部依赖、循环依赖风险

---

## Phase 2: 设计阶段（Framework Architect 主导）

**触发条件**: 审计完成，新功能开发

### 流程

```
1. 分析需求，确定接口设计
2. 设计模块结构和依赖关系
3. 编写接口定义（优先 Proto/Go interface）
4. Framework Architect 评审接口设计
5. 输出设计文档
6. 设计冻结
```

### 接口设计原则

1. **最小化接口**: 只暴露必要的方法
2. **职责单一**: 每个接口只有一个职责
3. **稳定优先**: 避免频繁破坏性变更
4. **可测试性**: 便于 Mock 和单元测试

### 产出物

| 文档 | 负责人 | 存放位置 |
|------|--------|---------|
| 接口设计 | Dev | `{docs_internal}/design/{module}/INTERFACE.md` |
| 评审记录 | Arch | `{docs_internal}/design/{module}/REVIEW.md` |

## Phase 3: 实现阶段（各模块 Dev 主导）

**触发条件**: 设计冻结后

### 流程

```
1. 创建功能分支
2. 实现接口（遵循契约优先原则）
3. 编写单元测试（覆盖率 ≥ 80%）
4. 编写 README 和使用示例
5. 提交 PR，触发 CI
6. Code Review
7. 合并到主分支
```

### 代码规范

```bash
# ⚠️ 必须先执行命令检测（见 SKILL.md 步骤 5）
# 检测到 go.mod → 后端：go fmt ./... && go vet ./... && golangci-lint run && go test ./... -cover && go build ./...
# 检测到 bun.lockb → 前端（bun）：bun run lint && bun run type-check && bun test && bun run build
# 检测到 pnpm-lock.yaml → 前端（pnpm）：pnpm run lint && pnpm run type-check && pnpm test && pnpm run build
# 检测到 package-lock.json → 前端（npm）：npm run lint && npm run type-check && npm test && npm run build
```

go get github.com/origadmin/{module}

## Phase 4: 测试阶段（QA + Dev 主导）

**触发条件**: 实现完成

### 流程

```
1. 单元测试验证
2. 性能基准测试
3. 边界条件测试
4. 依赖兼容性测试
5. 文档完整性检查
```

### 测试覆盖要求

| 指标 | 目标 |
|------|------|
| 单元测试覆盖率 | ≥ 80% |
| 核心逻辑覆盖率 | 100% |
| API 文档覆盖率 | 100% |

---

## Phase 5: 集成阶段（Framework Architect 主导）

**触发条件**: 各模块测试通过

### 流程

```
1. 集成测试（各模块配合）
2. 依赖冲突检查
3. 性能回归测试
4. Framework Architect 最终验收
5. 发布版本
```

### 发布检查清单

- [ ] 所有单元测试通过
- [ ] 集成测试通过
- [ ] 性能基准无退化
- [ ] 文档已更新
- [ ] CHANGELOG 已更新
- [ ] 版本号已更新

## 版本策略

### 语义化版本 (SemVer)

```
v{MAJOR}.{MINOR}.{PATCH}
  │     │     └── Patch: Bug 修复
  │     └─────── Minor: 新功能（向后兼容）
  └───────────── Major: 破坏性变更
```

### 模块独立版本

- 各子模块独立管理版本号
- `runtime` 接口破坏性变更需同步 `contrib`
- 定期同步依赖版本
