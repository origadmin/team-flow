## 3. 流程分析与改进（完整工作流）

**适用场景**：分析现有流程 → 设计改进方案 → 制定测试 → 逐步修复

### 3.1 工作流程（5 阶段）

```
阶段 1        阶段 2        阶段 3       阶段 4        阶段 5
流程分析  ──→  流程设计  ──→  BDD规约  ──→  TDD实现  ──→  逐步修复
   │              │              │              │              │
   ▼              ▼              ▼              ▼              ▼
analysis/      design/     requirements/   (测试代码)    (产品代码)
                                  │              │
                                  │    先写测试 ──┤
                                  │    再写实现 ──┤
                                  ▼              ▼
                           BEHAVIOR.md    biz/xxx_test.go
                           SCENARIOS.md   biz/xxx.go
```

**核心原则**：
- 阶段 3（BDD）定义**系统应该做什么**（行为规约）
- 阶段 4（TDD）定义**怎么验证做对了**（测试驱动）
- 阶段 5 按测试用例**逐个实现**，每实现一个跑一次测试

**⚠️ 禁止跳阶段**：必须按 1→2→3→4→5 顺序执行，不允许跳过 BDD/TDD 直接写实现代码

### 3.4 阶段 3: BDD 行为规约

**目标**：用自然语言定义系统行为，所有角色都能理解

**输出目录**：`{docs_internal}/requirements/{feature}/`

**输出文件**：
- `BEHAVIOR.md` - 行为规约（Given/When/Then 格式）
- `SCENARIOS.md` - 场景清单（按状态/接口拆分）

**输出格式**：
```markdown
# {功能} 行为规约

## Feature: {功能名称}

### Scenario: {场景名称}

**Given** 前置条件（系统当前状态）
**When** 用户操作（触发事件）
**Then** 预期结果（系统行为）

#### Examples:

| 参数 | 值 | 预期 |
|------|-----|------|
| file_size | 0 | 返回 INVALID_PARAM |
| file_size | 10GB | 返回 FILE_TOO_LARGE |
| file_size | 100MB | status=pending |

---

## 按状态的行为定义

### 状态: pending

**Given** 文件已上传，status=pending
- **When** 触发切片 → **Then** status 变为 processing，创建切片任务
- **When** 用户取消 → **Then** status 变为 cancelled，释放资源
- **When** 重复触发切片 → **Then** 返回 ALREADY_PROCESSING

### 状态: processing

**Given** 正在切片，status=processing
- **When** 切片完成 → **Then** status 变为 completed，progress=100
- **When** 切片失败 → **Then** status 变为 failed，error_code 有值
- **When** 再次触发 → **Then** 返回 ALREADY_PROCESSING

### 状态: completed

**Given** 切片完成，status=completed
- **When** 查询进度 → **Then** 返回 progress=100，返回切片列表
- **When** 重新上传 → **Then** 创建新记录，旧记录保留

### 状态: failed

**Given** 切片失败，status=failed
- **When** retry_count < 3 → **Then** 可重试，status→processing
- **When** retry_count ≥ 3 → **Then** 不可重试，返回 MAX_RETRY_EXCEEDED
```

### 3.5 阶段 4: TDD 测试驱动实现

**目标**：先写测试，再写实现，每个测试用例对应一个行为场景

**执行顺序**（严格按此顺序）：

```
1. 从 BEHAVIOR.md 读取场景
2. 将每个 Scenario 转化为测试用例
3. 先写测试代码（此时编译失败）
4. 再写最小实现（让测试通过）
5. 重构（测试仍然通过）
6. 重复 1-5 直到所有场景覆盖
```

**输出**：
- `biz/{feature}_test.go` - 测试代码（每个 Scenario 一个 Test 函数）
- `biz/{feature}.go` - 实现代码（仅实现让测试通过的最小代码）

**测试命名规范**：
```go
func Test{Feature}_{Scenario}_{ExpectedResult}(t *testing.T) {
    // Given
    // When
    // Then
}

// 示例：
func TestUploadSlice_NormalFile_StatusPending(t *testing.T) { ... }
func TestUploadSlice_EmptyFile_ReturnInvalidParam(t *testing.T) { ... }
func TestUploadSlice_OverSizeLimit_ReturnFileTooLarge(t *testing.T) { ... }
func TestUploadSlice_RetryExceeded_ReturnMaxRetryExceeded(t *testing.T) { ... }
```

**TDD 循环**：
```text
Red    → 写测试，运行失败（测试描述了期望行为）
Green  → 写最小实现，测试通过（代码满足行为规约）
Refactor → 重构代码，测试仍然通过（保持正确性）
```

### 3.6 阶段 5: 逐步实现

**按 development-standards.md 执行**，每个子任务完成后更新文档。

**实施规则**：
- 每次只实现一个场景的测试+代码
- 实现完成后运行 `go test ./...` 确认通过（后端命令根据检测结果）
- 运行 `go build ./...` 确认编译通过（后端命令根据检测结果）
- 运行 `go fmt ./...` 确认格式正确（⚠️ 后端命令根据 SKILL.md 步骤 5 检测结果）
- 全部场景实现后，更新 SCENARIOS.md 标记完成状态

### 3.7 阶段门禁（强制！）

**⚠️ 每个阶段必须有产出物才能进入下一阶段。缺少产出物 = 门禁未通过。**

| 阶段 | 必须产出 | 门禁检查 | 通过条件 |
|------|---------|---------|---------|
| 1→2 | `analysis/{feature}/CURRENT_STATE.md` | 文件存在 + 包含问题诊断 | 有明确的改进方向 |
| 2→3 | `design/{feature}/STATE_MACHINE.md` | 文件存在 + 包含状态流转图 | 状态定义完整，无死状态 |
| 3→4 | `requirements/{feature}/BEHAVIOR.md` | 文件存在 + 包含 Given/When/Then | 每个状态至少 1 个 Scenario |
| 4→5 | `biz/{feature}_test.go` | 文件存在 + 编译通过 | 测试覆盖 BEHAVIOR.md 所有 Scenario |

**⚠️ 门禁未通过时**：
- ❌ 禁止进入下一阶段
- ❌ 禁止直接写实现代码
- ✅ 必须补充缺失的产出物后重新检查

### 3.8 阶段衔接与触发规则

**核心原则：每个阶段完成后，AI 必须主动提示用户选择下一步，禁止沉默等待。**

#### 3.8.1 主动提示规则（⚠️ 强制执行！）

**每个阶段产出物写入后，AI 必须输出以下格式的提示：**

```
📋 阶段 {N} 已完成：{阶段名称}

📄 产出物：
- {产出文件1} — {简要说明}
- {产出文件2} — {简要说明}

👉 请选择下一步：
  [A] ✅ 审核通过，进入下一阶段（{下一阶段名称}）
  [B] 🔄 部分需要修改：{指出具体哪里需要改}
  [C] ❌ 整体重做，重新执行本阶段
  [D] ⏸️ 暂停，记录进度稍后继续
```

**⚠️ 禁止**：
- ❌ 阶段完成后沉默等待用户输入
- ❌ 假设用户会自动推进到下一阶段
- ❌ 只输出"阶段X已完成"不给选项

**每个阶段的选项模板**：

| 阶段完成后 | 选项 A | 选项 B | 选项 C | 选项 D |
|-----------|--------|--------|--------|--------|
| 1. 流程分析 | 通过，开始流程设计 | 修改：指出分析哪里不对 | 重新分析 | 暂停 |
| 2. 流程设计 | 通过，开始BDD规约 | 修改：指出设计哪里要改 | 重新设计 | 暂停 |
| 3. BDD规约 | 通过，开始TDD测试 | 修改：指出规约哪里要改 | 重新写规约 | 暂停 |
| 4. TDD实现 | 通过，开始逐步实现 | 修改：指出测试哪里要改 | 重新写测试 | 暂停 |
| 5. 逐步实现 | 全部完成，更新进度 | 修改：指出实现哪里要改 | 回退到TDD重做 | 暂停 |

#### 3.8.2 修改/驳回流程

**当用户选择 [B] 修改时，执行以下流程：**

```
用户: "B — 状态机里上传审核应该有驳回状态，不是只有通过"
           ↓
1. 记录修改请求到 PROGRESS.md 的 revision 字段
2. 仅修改用户指出的部分，保留用户未提及的内容
3. 修改完成后，重新输出 📋 提示（回到审核状态）
           ↓
用户再次选择: [A] 通过 / [B] 继续修改 / [C] 重做 / [D] 暂停
```

**修改规则**：
- ✅ 只改用户指出的问题，不改用户没提的
- ✅ 修改后必须重新走审核（输出 📋 提示）
- ✅ 在 PROGRESS.md 记录修改次数和内容
- ❌ 禁止修改后直接推进到下一阶段（必须再审核）
- ❌ 禁止擅自修改用户未提及的部分

**当用户选择 [C] 整体重做时：**
- 删除本阶段产出物
- 从头执行本阶段
- 完成后重新输出 📋 提示

**修改次数告警**：
- 同一阶段修改 ≥ 3 次时，输出提示：`⚠️ 本阶段已修改 {N} 次，建议明确核心需求后再继续`
- 同一阶段修改 ≥ 5 次时，输出提示：`🚨 本阶段已修改 {N} 次，强烈建议暂停讨论需求`

#### 3.8.3 参考分析 → 改进流程衔接

**流程 A: 参考分析（单次完成，停在审核点）**

```
用户: "分析 mediacms，对比差异，提改进建议，供我审核"
           ↓
执行: 阶段 1（分析 + 对比 + 建议）
产出: analysis/{feature}/CURRENT_STATE.md + suggestions.md
           ↓
输出 📋 提示:
  [A] ✅ 审核通过，开始流程设计
  [B] 🔄 部分修改：{指出哪里}
  [C] ❌ 重新分析
  [D] ⏸️ 暂停
```

**流程 B: 审核通过 → 按阶段推进**

```
用户选择 [A]
           ↓
门禁检查: suggestions.md 是否存在？
  ├─ 不存在 → 提示 "没有找到审核文档，请先完成参考分析"
  └─ 存在 → 执行阶段 2
           ↓
阶段 2 完成 → 输出 📋 提示 → 等待用户选择
  ↓ [A]
阶段 3 完成 → 输出 📋 提示 → 等待用户选择
  ↓ [A]
... 依此类推
```

**流程 C: 分阶段推进（用户指定跳到某阶段）**

如果用户在选项之外明确说"开始写测试"等：

| 用户说 | 触发 | 动作 |
|--------|------|------|
| 方案可以，直接写规约/BDD | 跳阶段 2 | 检查门禁 → 进入阶段 3 |
| 规约 OK，直接写测试/TDD | 跳阶段 3 | 检查门禁 → 进入阶段 4 |
| 先做 xxx，其他后面再说 | 子集执行 | 仅对指定功能执行全流程 |

**⚠️ 即使跳阶段，门禁检查仍然有效**：
- 用户说"写测试"但 BEHAVIOR.md 不存在 → 拒绝，要求先完成 BDD

#### 3.8.4 触发关键词汇总

| 用户输入 | 匹配 | 动作 |
|---------|------|------|
| 通过/可以/按方案来/审核通过/A | 阶段推进 | 进入下一阶段 |
| 修改/改一下/不对/这里有问题/B | 修改 | 进入修改流程 |
| 重做/重新来/C | 重做 | 删除产出物，重新执行 |
| 暂停/等等/先不做/D | 暂停 | 记录进度，停止 |

| 先做 xxx | 子集执行 | 仅对指定功能执行 |
